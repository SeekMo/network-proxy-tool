## 一、与 Shadowrocket 的关键差异

| 项目 | Shadowrocket | Stash |
|---|---|---|
| 配置格式 | `.conf`，分 `[段名]` | **`.yaml`，Clash 系语法** |
| 扩展方式 | 模块（`.sgmodule`） | 覆写（`.stoverride`） |
| DNS 配置 | `[General]` 的 `dns-server` | `dns:` 块下的 `nameserver`、`fallback` 等 |
| 不使用 Fake-IP 的域名 | `always-real-ip` | `fake-ip-filter` |
| 规则写法 | `DOMAIN-SUFFIX,xxx,策略` | `- DOMAIN-SUFFIX,xxx,策略`（YAML 列表） |
| 兜底规则 | `FINAL,策略` | `MATCH,策略` |
| WebRTC / STUN | `stun-response-ip`，或 App 内「禁用STUN」 | **待确认是否有等价能力** |

> 💡 **WebRTC 防护思路可能需要另行设计。** 若 Stash 没有协议级的 STUN 处理能力，就只能依赖「让 UDP 都走代理」这条路，防护强度弱于其他三个客户端。

## 二、已知问题（优化阶段需处理）

### 1. HTTPDNS 覆写存在 DNS 泄露风险

`Stash-HTTPDNS.Block.stoverride` 中有 **16 条 `IP-CIDR` 规则未带 `no-resolve`**（B站那组 HTTPDNS IP）。若启用该覆写，未被前面规则命中的域名走到这里都可能触发本地 DNS 解析。

**处理方向**：改为自建覆写并补上 `no-resolve`，或者不启用。

### 2. 全文仅出现 2 处 `no-resolve`

说明配置内绝大多数 IP 类规则都没有该参数。需在优化阶段逐项核查：

- `rules:` 段内的 IP 类规则
- `- GEOIP, CN, DIRECT`（当前未带 `no-resolve`）
- 各远程规则集内部的 IP 规则

**待确认**：Stash 对 IP 类规则的处理方式是否与 Shadowrocket 一致，即遇到时会先解析域名。

### 3. DNS 段需整体核查

`dns:` 块、`nameserver`、`fallback`、`fake-ip-filter` 均需按 Shadowrocket 的同样标准检查：是否混有明文 DNS、是否会退回系统 DNS、`fake-ip-filter` 内是否有会被污染的境外域名。

### 4. 检测站是否被规则集分到直连，需核实

Shadowrocket 与 QuantumultX 的 China 规则集都收录了 `browserleaks.com`。Stash 使用的规则集需同样核实，否则测试结果会失真。

## 五、注意事项

### 判定顺序不能颠倒：先确认 IP，再看 DNS

先看检测页顶部的 IP 是不是节点 IP。**若是真实 IP，说明该站没走代理，后面的 DNS 结论一律无效。**

### 「出现腾讯、阿里」是否算泄露，取决于域名本该走哪条路

| 域名类型 | 解析来源 | 判定 |
|---|---|---|
| 国内直连域名 | 腾讯、阿里 | ✅ 正常，可分到就近 CDN |
| 走代理的境外域名 | 节点那一侧 | ✅ 正常 |
| 走代理的境外域名 | 腾讯、阿里 | ❌ 异常，说明触发了本地解析 |
| 任意域名 | 当前运营商 | ❌ 最严重 |

### YAML 格式对缩进敏感

Stash 配置是 YAML，**缩进错误会导致整段配置失效甚至无法加载**。修改后建议先确认配置能正常加载，再开始测试。
